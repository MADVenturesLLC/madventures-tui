# @mad/single-verdict

> Single Verdict v0 — one closed-enum, Founder-facing ship/hold verdict per
> subject. Mission Control may only DISPLAY it.
>
> **LIBRARY — NOT PHASE_0 — NOT OCCUPANCY — NOT MISSION CONTROL.**

## The closed enum

`SHIP | HOLD | VERIFY_PASS | VERIFY_PASS_WITH_FINDINGS | VERIFY_FAIL | BLOCKED | STALE_EVIDENCE | SPEC_ONLY`

Every verdict record requires: `subject { name, sha }`, `reason_code` (closed
set, and only codes allowed for that verdict), `produced_by`, `produced_at`,
and structured `evidence_refs` (same shape as @mad/build-memory evidence, plus
an optional @mad/claim-boundary per link). Optional `findings[]`.

## Three gates — fake green is unrepresentable

1. **Memory gate** — positive verdicts (`SHIP`, `VERIFY_PASS`,
   `VERIFY_PASS_WITH_FINDINGS`) require build-memory status `VALID` for the
   subject. `STALE`/`UNKNOWN` is refused (`MEMORY_STALE_REQUIRES_REBIND`);
   the re-bind path is a fresh `@mad/build-memory` record, then retry. There
   is no override flag.
2. **Claim gate** — a link carrying a claim-boundary at rung R forbids any
   claim above R. `SHIP` asserts `merge`; `VERIFY_PASS*` asserts
   `verification`. A forbidding rung refuses the verdict
   (`CLAIM_FORBIDDEN_BY_RUNG`). claim-boundary is imported as-is — never
   weakened, never re-implemented. (v0 boundary, stated honestly: absence of
   any boundary does not itself block a verdict; the forbid-rule does.)
3. **Schema gate** — validation is fail-closed over closed enums: unknown
   fields, unknown verdicts, unknown reason codes, and reason codes not
   allowed for the verdict are structurally invalid.

Factory refusals throw `VerdictRefusal` — never a silent downgrade.

## For UIs

```ts
import { assertDisplayable, VERDICT_TONE } from "@mad/single-verdict";
const verdict = assertDisplayable(rawJson); // throws before anything renders
const tone = VERDICT_TONE[verdict.verdict]; // the ONLY color vocabulary
```

`assertDisplayable` is the only door: a UI that cannot parse a verdict cannot
display one, so it cannot invent one. `VERDICT_TONE` is total over the enum:
`SHIP/VERIFY_PASS=emerald`, `HOLD/VERIFY_PASS_WITH_FINDINGS=amber`,
`VERIFY_FAIL/BLOCKED=rose`, `STALE_EVIDENCE=zinc`, `SPEC_ONLY=violet`.
No "pretty green" exists without a verdict object behind it.

## Serialization

`serializeVerdict` emits byte-stable JSON (fixed key order). The committed
`test/goldens/*.json` are generated by the serializer itself
(`bun packages/single-verdict/test/generate-goldens.ts`) and pinned by tests.

## What this is NOT

- **NOT a decision-maker.** It produces verdicts from evidence; only the
  Founder acts on them.
- **NOT Phase 0 / occupancy / Gateway honesty.** Claim vocabulary:
  `SINGLE_VERDICT_V0`, `PROJECTOR_FIXTURE`. Forbidden:
  `PHASE_0`, `OCCUPANCY_PROOF`, `GATEWAY_HONESTY`, `ROOM_RUNTIME`,
  `PRODUCTION_MERGE_AUTHORITY`.
